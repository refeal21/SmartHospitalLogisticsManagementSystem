# 客户物联数据接入最小真实持久化架构

## 目标

把客户物联数据接入模型从内存目录推进到可持久化数据底座，支撑强电、暖通、给排水、医气、环境质量、污水站等监测点位、阈值规则和遥测读数的重启恢复。本文只保存脱敏后的系统目录和 mock 点位，不保存客户真实点位表、真实 IP、协议账号或现场数据。

## 决策

### ADR-008：物联目录与读数第一轮使用 SQLite，生产目标预留业务库 + 时序库

**状态：** 已接受。

**背景：** IoT 是后勤系统从“人工工单”进入“感知告警”的关键底座。目录、阈值和读数如果只在内存中，环境预警、医气压力异常、污水指标超限和工单联动都无法真实验证。

**决策：** 第一轮使用 SQLite 保存系统目录、监测点位、阈值规则和最近读数。表前缀采用 `iot_`。生产目标是 PostgreSQL 保存点位主数据和阈值配置，时序库或 TimescaleDB 保存高频遥测历史。

**取舍：**
- 正向：无需真实设备和时序库即可验证点位目录、阈值判定、读数入库和重启恢复。
- 正向：点位模型保留 BIM 空间、设备编码、协议适配器和来源证据，后续接真实 IoT 适配器时边界清楚。
- 负向：SQLite 不适合高频采集和长期时序分析；生产化必须引入批量写入、冷热分层和时序保留策略。

### ADR-009：读数入库保存风险判定结果快照

**状态：** 已接受。

**背景：** 阈值规则可能会调整。如果只保存原始值，历史告警复盘时无法还原当时系统为什么判定为 Warning 或 Critical。

**决策：** `iot_telemetry_readings` 同时保存原始值、单位、采集时间、风险等级和规则命中摘要。后续规则版本化时，再补 `rule_version` 或规则快照表。

**取舍：**
- 正向：历史读数可直接用于告警列表、趋势摘要和审计复盘。
- 正向：前端详情不必每次重新计算历史风险。
- 负向：规则调整后历史风险不会自动重算；这是审计场景可接受的取舍。

## 第一轮持久化范围

| 表 | 是否实现 | 原因 |
| --- | --- | --- |
| `iot_system_profiles` | 是 | 保存客户系统分类、子系统、角色和使用端 |
| `iot_monitoring_points` | 是 | 保存点位、BIM 位置、设备编码、协议适配器、指标字段和来源证据 |
| `iot_threshold_rules` | 是 | 保存点位指标的预警/严重阈值和规则摘要 |
| `iot_telemetry_readings` | 是 | 保存最近读数、风险等级和规则命中说明 |
| `iot_alarm_events` | 暂缓 | 告警事件需要与工单、通知、确认/处置联动，下一轮做 |
| `iot_adapter_mappings` | 暂缓 | 真实协议字段映射需等待现场接入信息 |
| `iot_time_series_archive` | 暂缓 | 高频历史数据后续交给 TimescaleDB 或独立时序库 |

## 表结构约束

- 系统分类使用 `category` 作为主键，便于和领域枚举对齐。
- 点位使用 `point_code` 作为主键，并拆列保存空间/BIM 字段。
- 指标定义、来源证据、子系统、角色、使用端第一轮用 JSON 文本保存。
- 读数值用字符串保存 decimal，避免 SQLite 浮点精度干扰；应用层按 decimal 解析。
- 读数保存 `risk_level` 和 `rule_summary`，形成历史风险快照。

## 验收标准

1. 使用同一个 SQLite 文件接入一条医气压力异常读数后，新建服务实例仍能读到该读数和 Critical 风险。
2. 使用同一个 SQLite 文件初始化目录后，新建服务实例仍能读到系统、点位、阈值和种子读数。
3. 未知点位返回 404，未知指标返回 400，且不写入读数。
4. 原有内存模式测试继续通过。
5. 原始客户点位表、真实设备数据、协议凭据、日志、缓存和数据库文件不进入 Git 提交。

# 资产台账与巡检保养最小真实持久化架构

## 目标

把资产台账与巡检保养从内存纵切推进到可持久化业务底座，支撑设备设施、BIM 空间位置、巡检计划、巡检任务、检查结果、生命周期记录和异常转工单链路的重启恢复。本文只定义脱敏后的工程模型，不保存原始 PPT、客户调研表、竞品原文或客户真实数据。

## 决策

### ADR-006：资产巡检第一轮沿用 SQLite，生产目标仍保持 PostgreSQL

**状态：** 已接受。

**背景：** 资产台账是后勤系统的底座之一，后续工单、BIM、IoT、能耗、合同、质量都会引用它。若继续只放内存，巡检执行结果、异常工单号和生命周期无法审计，也无法验证页面与 API 是否真正闭环。

**决策：** 第一轮使用 SQLite 文件库实现资产巡检持久化，表前缀采用 `asset_`，字段命名按 PostgreSQL 目标靠拢。后续 PostgreSQL 阶段保留同名表、外键、审计字段和事务语义。

**取舍：**
- 正向：无需安装外部数据库即可验证真实落库、重启恢复和异常转工单结果。
- 正向：资产、计划、任务、生命周期先形成稳定边界，后续能被 BIM、IoT、工单模块引用。
- 负向：SQLite 不承担生产多实例并发、复杂检索和全文/附件能力；生产化仍需 PostgreSQL 迁移与集成测试。

### ADR-007：巡检任务完成与生命周期事件必须同事务保存

**状态：** 已接受。

**背景：** 医院设备巡检涉及安全、外包考核、事故复盘和合同履约。如果任务状态更新成功但生命周期记录缺失，就会出现审计断链。

**决策：** 应用层定义 `IAssetMaintenancePersistence`，Infrastructure 层实现 SQLite 仓储。正常完成、异常待维修、异常转工单都通过仓储事务同时保存任务结果和生命周期事件。

**取舍：**
- 正向：任务状态、检查结果、完成人、异常工单号和审计事件保持一致。
- 正向：应用服务继续只处理领域规则，不直接写 SQL。
- 负向：第一轮仍是单服务快照加载，后续需要补乐观锁、人员组织外键和真实工单模块联动。

## 第一轮持久化范围

| 表 | 是否实现 | 原因 |
| --- | --- | --- |
| `asset_ledger_items` | 是 | 设备设施台账是巡检、工单、BIM、IoT 的引用底座 |
| `asset_maintenance_plans` | 是 | 巡检/保养计划定义任务来源、周期、模板和责任班组 |
| `asset_maintenance_tasks` | 是 | 保存执行状态、检查结果、完成人、异常工单号 |
| `asset_lifecycle_events` | 是 | 保存计划保养、告警联动、完成巡检、异常转工单等审计事件 |
| `asset_spare_parts` | 暂缓 | 备件库存应由仓库耗材模块统一建模 |
| `asset_contract_links` | 暂缓 | 合同履约由综合管理/合同模块统一建模 |
| `twin_spatial_refs` | 暂缓 | 当前空间字段仍内嵌，BIM 空间模块深挖时独立主数据 |
| `wo_work_orders` 联动 | 暂缓 | 当前异常转工单先保存工单号，下一轮做跨模块事务或事件集成 |

## 表结构约束

- 主键沿用业务编码：`asset_code`、`plan_code`、`task_no`，便于现场调试和后续系统对账。
- 空间字段拆列保存：院区、楼栋、楼层、房间、BIM 构件。
- 状态、优先级、任务类型、结果类型保存字符串，便于跨前后端调试和迁移。
- 检查模板、检查结果、来源证据、来源标签第一轮用 JSON 文本保存，后续可拆为子表。
- 生命周期记录不可替代任务当前状态；任务表保存当前状态，生命周期表保存过程审计。

## 验收标准

1. 使用同一个 SQLite 文件完成正常巡检后，新建服务实例仍能读到任务完成状态、检查结果和生命周期记录。
2. 使用同一个 SQLite 文件完成异常巡检并转工单后，新建服务实例仍能读到 `ConvertedToWorkOrder` 状态和 `WO-MT-*` 工单号。
3. 已关闭任务不会再次出现在到期任务池中。
4. 原有内存模式测试继续通过。
5. 原始资料、客户数据、PPT 导出、日志、缓存和数据库文件不进入 Git 提交。

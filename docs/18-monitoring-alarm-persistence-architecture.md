# 监测告警预警池最小真实持久化架构

## 目标

把 IoT 异常读数推进为可持久化、可确认、可转工单的预警事件，形成“点位采集 -> 阈值判定 -> 预警池 -> 告警确认 -> 处置工单”的最小闭环。本文只保存脱敏后的事件模型和 mock 数据，不保存真实设备数据、协议凭据或现场系统信息。

## 决策

### ADR-010：告警事件独立于遥测读数保存

**状态：** 已接受。

**背景：** 遥测读数是事实流，告警事件是运营处置对象。一个读数可能触发告警，但告警有确认、责任班组、处置工单、关闭等业务状态，不能只靠读数表表达。

**决策：** 新增 `iot_alarm_events` 保存预警事件。IoT 服务接入 Warning/Critical 读数后，通过 `IMonitoringAlarmRecorder` 生成预警事件。告警服务负责查询预警池、确认告警和标记转工单。

**取舍：**
- 正向：读数历史和处置过程分离，便于趋势分析和运营闭环分别演进。
- 正向：医气、污水、供配电、环境质量等专项系统共用同一预警池。
- 负向：本轮只保存转工单号，尚未把新工单注入工单服务运行态；下一轮需要做跨模块事件或统一工作流事务。

### ADR-011：预警事件保存风险判定和空间快照

**状态：** 已接受。

**背景：** 点位名称、BIM 构件、空间归属和阈值策略可能随时间变化。事故复盘时需要知道当时告警发生在哪个空间、命中了什么规则。

**决策：** 告警事件保存点位、指标、风险等级、空间/BIM、读数值、单位、触发时间、规则摘要、责任班组、确认人、处置工单号和最后备注。

## 第一轮持久化范围

| 表 | 是否实现 | 原因 |
| --- | --- | --- |
| `iot_alarm_events` | 是 | 预警池、确认、转工单、空间定位和审计复盘的主记录 |
| `iot_alarm_transitions` | 暂缓 | 本轮用主记录字段表达最后状态，后续补完整流转审计 |
| `wo_work_orders` 联动 | 暂缓 | 本轮保存 `WO-ALM-*` 工单号，下一轮接入工单状态机 |
| `msg_notifications` | 暂缓 | 消息推送由待办/消息模块统一设计 |

## 验收标准

1. Critical/Warning 遥测读数能自动生成预警事件。
2. 使用同一个 SQLite 文件重启告警服务后，预警事件仍可查询。
3. 告警确认和转工单状态能持久化。
4. 告警事件保留 BIM 空间位置、风险等级、责任班组和规则摘要。
5. 原有工单、资产、IoT 测试继续通过。

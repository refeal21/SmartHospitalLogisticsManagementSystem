# 一站式服务最小真实持久化架构

## 目标

把一站式服务从内存数据推进到可持久化的真实业务底座，同时避免一次性铺开全平台数据库导致返工。本文约束第一轮数据库实现：只持久化服务受理到工单闭环所必需的数据，并保留未来迁移 PostgreSQL 的结构空间。

## 决策

### ADR-004：V1 开发环境使用 SQLite 文件库，生产目标保持 PostgreSQL

**状态：** 已接受。

**背景：** 项目处于 0 到 1 的领域模型验证期。当前机器未确认 PostgreSQL 服务可用，直接依赖外部数据库会拖慢前端/API/状态机闭环验证。但数据库层不能继续停留在内存数组，否则刷新、重启、幂等、审计都无法真实验证。

**决策：** 第一轮实现使用 SQLite 文件库作为本地开发和自动化测试的真实持久化层，表结构、命名、外键、审计字段和状态字段按 PostgreSQL 目标设计。应用层只依赖仓储接口，后续可替换为 PostgreSQL 实现。

**取舍：**
- 正向：无需安装外部服务即可验证真实落库、重启恢复、唯一约束和时间线持久化。
- 正向：表结构先按业务对象稳定，后续迁移 PostgreSQL 时不会重写领域层。
- 负向：SQLite 不覆盖 PostgreSQL 的全部并发、索引和 JSON/时序能力；后续生产化必须补 PostgreSQL 集成测试。

### ADR-005：先做仓储接口，不把应用服务绑定到数据库实现

**状态：** 已接受。

**背景：** 当前 `WorkOrderDispatchService` 承担工单状态机和用例编排。如果直接在服务中写 SQL，会让业务规则和数据库细节耦合，后续迁移 PostgreSQL 或拆分仓储会很痛。

**决策：** 在 Application 层定义持久化接口和快照对象；Infrastructure 层实现 SQLite 仓储。应用服务启动时从仓储加载快照，状态变化后通过仓储保存工单、服务请求和流转事件。

**取舍：**
- 正向：领域状态机可测试，数据库实现可替换。
- 正向：当前内存测试不被数据库拖慢。
- 负向：第一轮仍是单服务内加载快照，尚未解决多实例并发，需要 PostgreSQL 阶段补乐观锁和事务边界。

## 第一轮持久化范围

| 表 | 是否实现 | 原因 |
| --- | --- | --- |
| `wo_service_requests` | 是 | 服务受理必须可恢复，并能幂等转工单 |
| `wo_work_orders` | 是 | 工单池、详情、状态机的主记录 |
| `wo_work_order_transitions` | 是 | 每个派工、接单、挂单、完工、验收、评价必须审计 |
| `wo_dispatch_assignments` | 暂缓 | 当前派工责任先保存在工单和流转中，下一轮补当前/历史责任 |
| `wo_service_evaluations` | 暂缓 | 当前评价先进入流转记录，服务品质深挖时独立建表 |
| `wo_sla_policies` | 暂缓 | 当前 SLA 用种子规则和截止时间，后续配置化 |
| `twin_spatial_refs` | 暂缓 | 当前空间作为工单/请求内嵌字段，BIM 空间模块深挖时独立主数据 |

## 表结构约束

第一轮 SQLite 表字段尽量与 `docs/14-one-stop-service-domain-data-model.md` 对齐：

- 主键先用业务编号：`request_no`、`work_order_no`，避免过早引入 UUID 迁移复杂度。
- 空间字段拆列保存：院区、楼栋、楼层、房间、BIM 构件。
- 状态和优先级保存字符串，便于跨前后端调试和迁移。
- 流转记录必须保存 `action`、`from_status`、`to_status`、`operator_name`、`remark`、`rating`、`occurred_at`。
- `wo_service_requests.converted_work_order_no` 唯一表达幂等转换结果。

## 非目标

本轮不做：

- 全量 PostgreSQL 部署。
- EF Core 迁移体系。
- 用户、权限、组织、岗位全表。
- 附件对象存储。
- IoT 时序库。
- 资产、BIM、合同、质量全量主数据。

## 验收标准

1. 使用同一个 SQLite 文件创建服务请求并转工单后，新建一个服务实例仍能读到该工单。
2. 工单派工、接单、完工、验收、评价后，新建服务实例仍能读到最新状态和流转记录。
3. 同一个服务请求重复转换，不生成重复工单。
4. 原有内存模式测试继续通过。
5. API 和前端在 API 可用时优先走持久化链路；API 不可用时前端仍可 fallback 到本地演示数据。
